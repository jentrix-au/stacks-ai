# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Stacks" — a Trello-style task manager. Next.js 16 (App Router, React 19) on Vercel, Postgres via Prisma 7 (Neon in prod), Auth.js v5 with database sessions, Pusher Channels for realtime, Cloudflare R2 for attachments, Resend for emails. Same task operations are exposed as both Server Actions (UI) and MCP tools (agents) over a single core in `src/server/tasks/operations.ts`.

User-facing documentation lives in `docs/` (user guide, agent platform reference, agent setup variants, deployment) and is rendered in-app at `/docs` (`src/app/docs`, statically generated; manifest + relative-link rewriting in `src/lib/docs.ts` / `src/lib/docs-links.ts` — a unit test keeps the manifest in sync with the directory, so adding a doc file requires a manifest entry). Update the relevant doc when changing user-visible behavior or the MCP/webhook contracts.

## Commands

Use `pnpm` (workspace pinned). Common scripts:

- `pnpm dev` — Next dev server on :3000.
- `pnpm build` — runs `prisma generate && prisma migrate deploy && next build` (the migrate step requires a reachable DB).
- `pnpm typecheck` — `tsc --noEmit`. Run before declaring TS work done.
- `pnpm lint` / `pnpm lint:fix` — ESLint (Next + TS + Prettier).
- `pnpm format` / `pnpm format:check` — Prettier (with tailwindcss plugin).
- `pnpm test` — Vitest (unit). Single test: `pnpm test path/to/file.test.ts -t "name"`.
- `pnpm test:e2e` — Playwright; auto-starts `pnpm dev --port 3100`. Single spec: `pnpm test:e2e tests/e2e/board.spec.ts`. E2E auth uses `POST /api/dev/sign-in` (dev-only) to log in as the seeded demo user.
- DB: `pnpm db:migrate` (dev migration), `pnpm db:deploy` (apply in CI/prod), `pnpm db:push` (prototype), `pnpm db:studio`, `pnpm db:seed` (idempotent demo workspace).

Env: copy `.env.example` to `.env.local`. `DATABASE_URL` is required for any DB use; `DIRECT_URL` is for migrations. `prisma.config.ts` loads `.env.local` then `.env` and tolerates a missing URL (placeholder) so `postinstall` doesn't fail on a fresh checkout. Pusher/R2/Resend are optional in dev — code silently no-ops when their env vars are absent.

## Architecture

### Request flow (UI side)
App Router pages live under `src/app/[workspaceSlug]/…`. Pages are Server Components that call query helpers in `src/server/queries/*` (wrapped in React `cache`). Mutations go through Server Actions in `src/server/actions/*`, which validate with Zod schemas from `src/server/tasks/schemas.ts` and delegate to the core in `src/server/tasks/operations.ts` (and analogous `columns.ts`, `boards.ts`, etc.). The board UI in `src/components/board/board-client.tsx` is the main interactive surface (dnd-kit + optimistic state + realtime).

### Operations core
`src/server/tasks/operations.ts` is the single source of truth for task mutations. Each function:
1. Calls `requireWorkspaceRole` / `requireBoardAccess` / `requireTaskAccess` from `src/lib/authz.ts` — these throw `AuthzError` (mapped to 403/404). **Every mutation must go through one of these checks at the top.**
2. Runs the DB write (often in `db.$transaction` with an `Activity` row).
3. Calls `revalidatePath` for the board route.
4. Fires a Pusher event via `triggerBoardEvent`.

Each op takes a `source: "ui" | "mcp"` so activity payloads can be attributed correctly.

### Server Actions vs MCP tools (same core)
`src/server/actions/*.ts` (UI) and `src/lib/mcp/tools.ts` (agents) both call `ops.*` with the same Zod schemas. The ops core is `src/server/tasks/operations.ts` plus sibling modules — `boards/` (create/rename/convert), `columns/`, `labels/`, `comments/`, `subtasks/`, `contacts/` — each pairing `operations.ts` with `schemas.ts`; server actions are thin session shims over these (P2.3 moved the last inline action logic into the core). The MCP server is mounted at `/api/[transport]` via `mcp-handler` and authenticated by Bearer PAT (`Authorization: Bearer tm_…`) validated against `ApiToken.tokenHash` (sha256, constant-time compare) in `src/lib/api-tokens.ts`. Per-token rate limits live in `ApiTokenRateLimit`. When adding a new task mutation, expose it through both surfaces and reuse the schema.

**Token scopes (P2.1).** `ApiToken.scopes` is a `String[]` of `read` / `write` / `admin` (constants + helpers in `src/lib/token-scopes.ts`; exact-match classes, no hierarchy). Every MCP tool declares its class in its `safe(extra, toolClass, fn)` wrapper — reads need `read`, mutations `write`, structural/destructive tools (`convert_board_kind`, later webhooks/automations) `admin`; violations return a structured `FORBIDDEN` envelope before the op runs. **Every new MCP tool must pass the correct class to `safe()`.** An empty `scopes` array means the token predates scoping and is grandfathered as full access until rotated (the tokens UI nags). `ApiToken.workspaceId` (nullable) pins a token to one workspace: `safe()` runs the handler inside `runWithWorkspaceRestriction` (`src/lib/authz-context.ts`, AsyncLocalStorage) and `requireWorkspaceRole` — the choke point all authz helpers funnel through — rejects any other workspace; `list_workspaces` filters to the allowed one. UI server actions never set this context, so session auth is unaffected.

**MCP error envelope.** Every tool handler is wrapped by `safe()` in `src/lib/mcp/tools.ts`; failures always return `isError: true` with JSON `{ error: { code, message, hint } }` where `code` ∈ `FORBIDDEN | NOT_FOUND | INVALID_INPUT | RATE_LIMITED | CONFLICT | INTERNAL` (mapping in `src/lib/mcp/errors.ts` — throw `AuthzError` with the right status, never plain `Error`, for domain failures). Rate-limited requests still authenticate but carry `authInfo.extra.rateLimit`; each tool call then returns `RATE_LIMITED` with `retryAfterSeconds` (an HTTP 429 is impossible — `withMcpAuth` turns any verify failure into a generic 401 that agents read as a dead token). Tools can override the generic hint per error code via `safe()`'s fourth argument (`HintOverrides`).

**MCP tool quality contract (P2.2).** Every tool declares: spec **annotations** (`readOnlyHint` on reads, `destructiveHint` on `archive_*`/`convert_board_kind`, `idempotentHint` on set/update/link tools, `openWorldHint: false` everywhere — use the `READ`/`WRITE_IDEMPOTENT`/`WRITE_CREATES`/`DESTRUCTIVE` constants in `tools.ts`) and an **`outputSchema`** (zod, in `src/lib/mcp/output-schemas.ts`); `ok()` returns compact-JSON text plus `structuredContent`, which the SDK validates against the schema (a mismatch is a thrown protocol error — keep serializer and schema in sync). Every tool result is an object — list tools wrap arrays (`{ boards: [...] }`); dates are ISO strings (convert at the query layer). `list_tasks`/`get_task`/`list_contacts` take `response_format: "concise" | "detailed"` (lists default concise, `get_task` defaults detailed); responses carry semantic names next to ids (`key`, `boardName`, `columnName`) and paginated lists return `totalCount` plus a `notice` string when truncated.

**MCP coverage (P2.3).** 46 tools. Orientation: `get_board_snapshot` (board+columns+concise tasks in one call), `search_tasks` (workspace-wide Postgres FTS + trigram substring fallback, matches comment bodies too — P3.1), `list_activity` (taskId/boardId + since/source/type filters — `source` separates humans from agents). Coverage: comments (`list/create/update/delete_comment` — edits author-only), subtasks (`create/toggle/delete_subtask`), `list_attachments` (short-lived signed URLs; uploads UI-only), consolidated `manage_labels` / `manage_columns` (action-param tools), `create_board`/`rename_board`, and bulk ops (`bulk_create_tasks` all-or-nothing in one column; `bulk_update_tasks`/`bulk_move_tasks` validate per item, apply valid writes in one transaction, return per-item results).

**Idempotency + concurrency (P2.4).** Every `create_*` and `bulk_*` MCP tool takes an optional `idempotencyKey` (handled by `withIdempotencyKey` in `src/lib/mcp/idempotency.ts`, stored in `IdempotencyKey` keyed by `[tokenId, key]`, 24h TTL): same key + same args replays the stored response; same key + different args is `CONFLICT`. Every `update_*` op and `move_task` takes an optional `expectedUpdatedAt` (in the SHARED Zod schemas — UI actions simply don't pass it): a mismatch throws `StaleWriteError` (`src/lib/authz.ts`) which maps to a `CONFLICT` envelope embedding the entity's **current** state under `error.current` so agents merge without an extra read (freshness helper in `src/lib/freshness.ts`; sidecar updates compare the sidecar's own `updatedAt`). New create-style tools must add the `idempotencyKey` param; new update-style ops must run `assertFresh`.

**MCP resources + prompts (P2.5).** Registered next to the tools in the same handler (`src/lib/mcp/resources.ts`, `src/lib/mcp/prompts.ts`). Resources (read-only JSON, `read` scope enforced, workspace restriction honored; guard failures THROW since resources have no `isError` channel): `stacks://workspace/{id}` (overview: boards+members+counts), `stacks://board/{id}` (concise snapshot), `stacks://task/{key}` (by human key — ambiguous prefixes across the user's workspaces are rejected with a pointer to `get_task`). The workspace template also lists the caller's workspaces concretely. Prompts (canned workflows over the tool surface): `triage_bugs`, `daily_standup`, `pipeline_review`, `sla_watch`.

**Outbound webhooks (P2.6).** `emitBoardEvent(boardId, event, payload)` in `src/lib/events.ts` is THE fan-out — it does Pusher + webhook enqueue; **ops must call it, never `triggerBoardEvent` directly** (that stays internal to the events layer). Deliveries persist in `WebhookDelivery` (PENDING/SUCCESS/FAILED); first attempt runs post-response via `after()`, retries via `/api/cron/webhooks-retry` (Vercel cron every 5 min, `CRON_SECRET`-guarded) with exponential backoff up to 8 attempts; 3 exhausted deliveries in a row auto-disable the webhook (`active=false`, delete+recreate to re-enable). SSRF guard (`src/lib/webhooks/security.ts`, run at creation AND before every delivery): https only, no credentials in URL, no localhost/private/link-local destinations (DNS-resolved), `redirect: "manual"`, 5s timeout; `STACKS_WEBHOOK_ALLOW_PRIVATE=1` bypasses it for local receivers in dev/tests ONLY. Management is ADMIN-role + admin-scope: workspace settings UI and the `create_webhook`/`list_webhooks`/`delete_webhook`/`list_webhook_deliveries` tools. Receivers verify deliveries like this:

```js
import { createHmac, timingSafeEqual } from "node:crypto";
// headers: X-Stacks-Signature, X-Stacks-Timestamp, X-Stacks-Event, X-Stacks-Delivery-Id
function verify(secret, headers, rawBody) {
  const expected =
    "sha256=" +
    createHmac("sha256", secret)
      .update(`${headers["x-stacks-timestamp"]}.${rawBody}`)
      .digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(headers["x-stacks-signature"] ?? "");
  return a.length === b.length && timingSafeEqual(a, b);
}
```

**OAuth 2.1 (P2.7).** The MCP endpoint accepts TWO bearer types through the same `verifyToken`: PATs (`tm_`) and OAuth access tokens (`tmo_` — ApiToken rows with 1h expiry created by the AS; refresh tokens `tmr_` are never bearers). RS: RFC 9728 PRM at `/.well-known/oauth-protected-resource` (+ path-aware `/api/mcp` variant) via `protectedResourceHandler`. AS (no new deps, `src/lib/oauth/`): RFC 8414 metadata at `/.well-known/oauth-authorization-server`; `GET /oauth/authorize` (Auth.js session + consent UI with scope/workspace pickers) issues 10-min single-use codes bound to PKCE S256 + exact `redirect_uri`; `POST /oauth/token` exchanges codes and rotates refresh tokens (single-use, paired access token revoked on rotation). Clients register via **CIMD**: `client_id` is an https URL whose metadata document is fetched through the webhook SSRF guard and cached in `OAuthClient` (1h TTL, stale-serve on fetch failure). No DCR (add only if a target client needs it). Grants inherit the scope/workspace model — everything in P2.1 applies to OAuth tokens unchanged.

**Agent attribution + usage (P2.8).** `withSource` lives in `src/server/activity.ts` (single shared implementation — never redefine it): MCP-sourced activity payloads automatically gain `tokenId`/`tokenName` from the per-request context (`runWithMcpRequestContext` set by `safe()`; `mcpActor()` reads it). The activity feed and comment thread render a "via 🤖 <token name>" badge (comments attribute via the `commentId` in COMMENT_CREATED payloads). `ApiTokenUsage` rolls up per-token daily `requests` (incremented in `verifyToken`) and `mutations` (incremented in `safe()` for write/admin calls); `/account/tokens` shows 7-day usage plus the token's recent actions. Dev-only `/api/dev/mcp-token` mints a demo-user PAT for e2e tests (pattern of `/api/dev/sign-in`).

The full surface (names, annotations, schemas) is frozen by `tests/mcp/tool-surface.test.ts`, result shapes by `tests/mcp/result-shape.test.ts` snapshots, and concise `list_tasks` size by `tests/mcp/token-cost.test.ts` (≤400 chars/task, ≤20k chars/page) — update those tests deliberately when the contract changes. New tools must follow all of the above.

**Global search (P3.1).** `src/server/queries/search.ts` is THE search layer: generated `tsvector` columns (`Task` title+description, `Contact` name+email+company, `Comment` body — declared `Unsupported("tsvector")` in the Prisma schema, actual DDL in the hand-authored migration) plus GIN and `pg_trgm` indexes. Matching is `websearch_to_tsquery` (`'english'` for tasks/comments, `'simple'` for contacts) OR a trigram-ILIKE substring fallback; comment matches surface the parent task; archived entities are excluded at every level. `searchWorkspace(userId, …)` powers the cmd-K palette (debounced `searchWorkspaceAction`) and `/[ws]/search`; cursor-paged `searchTasksPage` powers the `search_tasks` MCP tool (contract unchanged; matching is a strict superset of the old ILIKE). Task results deep-link as `/[ws]/board/[boardSlug]?task=<id>` — the board page hands `initialOpenTaskId` to `board-client.tsx`, which opens the detail panel; reuse this URL form for any "open task X" link.

**My Work (P3.2).** `/[ws]/my-work` groups the caller's open tasks — Overdue / Due today / Assigned to me, mutually exclusive — cross-board via `getMyWork` (`src/server/queries/my-work.ts`; day boundaries use the server clock, UTC in prod). A "recently mentioned" group joins in P3.3 once mention metadata exists. The workspace home shows a my-work digest + recent activity (`listWorkspaceActivity` in `src/server/queries/activity.ts`). Activity verb labels/icons live in `src/lib/activity-verbs.ts` (plain module shared by the client activity feed and server pages — don't redefine them in components). Tasks are completed by archiving: the detail panel header has the Archive button (wired to the `archiveTask` action; board client drops the card optimistically).

**Notifications (P3.3).** `src/server/notifications.ts` is the engine. Notification rows are written inside the mutating op's transaction (`createTaskNotifications`, payload = denormalized display snapshot: actorName/taskKey/taskTitle/boardSlug/preview); immediate emails (mention/assign ONLY, per-user `User.notifyEmail` toggle, UI on the inbox page) go post-response via `queueNotificationEmails` → `sendNotificationEmail` in `src/lib/email.ts` (no-ops without `AUTH_RESEND_KEY`; transport injectable for tests). Auto-watch (`ensureWatchers`): creator on create, newly-added assignees on assign (the op diffs current vs next), comment author on comment. Comment fan-out (`resolveCommentRecipients`): mentioned → `mentioned`, remaining watchers → `commented`, actor never notified. `Comment.mentions` stores mentioned user ids — the editor's @autocomplete records picks and drops ids whose label was edited out; the shared `CreateCommentSchema.mentions` param exposes mentions over MCP (must be workspace members, else INVALID_INPUT). Bell + unread count render in the topbar (layout calls `unreadNotificationCount`); `/[ws]/inbox` lists, click-through marks read, "Mark all read" clears. `Notification.type` is an OPEN STRING ("assigned" | "mentioned" | "commented"; P3.6 adds "due_soon"/"sla_breached") — deliberately not a DB enum. Inbox/mark-read have no MCP surface (user-private); the daily digest email lands with the P3.6 cron.

**Saved views (P3.4).** `SavedView` persists a named snapshot of the board-filter state — the nuqs URL params in `src/components/board/board-filters.tsx` (`labels`/`assignees`/`priorities`/`due` + the P3.4 `sort` key: priority | due | newest, null = manual positions) — validated by `ViewFiltersSchema` in `src/server/views/schemas.ts` (keep it in sync with the parsers). Ops in `src/server/views/operations.ts` (list = own + shared, create = any member, delete = creator or board ADMIN); UI-preference state by design: no Activity, no realtime, no MCP surface. Chips render in the board top bar (`saved-views.tsx`); applying a view writes the URL params, so filters survive reload. While `sort` is active the visible order is a view-time transform: same-column drags are ignored, cross-column drops append to the end of the target column.

**Dashboards + roadmap graph (P3.5).** `/[ws]/dashboards` renders per-kind metric cards (CRM pipeline by stage/owner + closing-this-quarter, SUPPORT open-by-severity/SLA-breaches/avg-first-response, BUGS open-by-severity/avg-resolution/reopened, ROADMAP by-quarter + blocked). Each kind = one cached fetch + one PURE aggregation in `src/server/queries/dashboards.ts` (`aggregateCrm` etc.) — unit-tested against seed-shaped fixtures; Deal.amount converts Decimal→Number at that boundary; charts are `recharts` in the `BarChartCard` client component (data passed as plain props from Server Components). `/[ws]/roadmap` is the dependency graph: `getRoadmapGraph` (`src/server/queries/roadmap-graph.ts`) returns all open initiatives + one-hop BLOCKS/DEPENDS_ON neighbors (cross-board blockers included) over `TaskLink`; `roadmap-graph.tsx` lays it out with `dagre` (LR) inside `@xyflow/react`, blocked nodes outlined red, node click deep-links to the task.

**Cron engine (P3.6).** `/api/cron/sweep` (Vercel cron every 5 min, `CRON_SECRET`-guarded; core in `src/server/cron/sweep.ts` with an injected clock) does four things: due-soon/overdue reminders (window 24h; at most TWO reminders per due date — entering-window and overdue — deduped by a `marker` stored in the notification payload; changing the due date re-arms), SLA breaches (`SLA_BREACHED` activity written with `actorId: null` in the SAME transaction as the notifications — the activity row IS the once-only marker), the idempotency-key TTL sweep, and the webhook retry drain (the sweep replaced the separate webhooks-retry cron entry in vercel.json; that route remains for manual runs). Sweep events fan out as `task.due_soon` / `ticket.sla_breached` through `emitBoardEvent`. `Activity.actorId` is now NULLABLE — null means system-generated; UIs render "System" and the MCP `list_activity`/`get_task` output schemas mark actorId nullable. `/api/cron/daily-digest` (daily 08:00 UTC) emails each opted-in user their unread notifications from the last 24h (`src/server/cron/daily-digest.ts` — the digest deferred from P3.3).

**Automations v1 (P3.7).** `AutomationRule` stores trigger/conditions/actions as Json validated by `src/server/automations/schemas.ts` (re-parsed at execution; malformed rules are skipped, never crash the pipeline). Triggers: `task.created`, `task.moved_to_column` (optional columnId), `label.added` (optional labelId), `due.passed`, `sla.breached` (the last two dispatched by the P3.6 sweep with source `"system"`). The executor (`src/server/automations/engine.ts`) is invoked post-commit/post-response by the ops core via `dispatchAutomationEvent` (createTask / moveTask / setTaskLabels — the latter gained a `source` param and an added-labels diff) and runs actions THROUGH the ops core as the rule's CREATOR with `source: "automation"` (`ActivitySource` is now `"ui" | "mcp" | "automation"` — a TS union, never a DB enum). **Hard loop guard: automation-sourced events return immediately — rules can never trigger rules.** Every run increments `runCount` and writes an `AUTOMATION_RAN` activity (actorId null, payload carries ruleId/ruleName). The `fire_webhook` action emits the `automation.fired` board event. Management: board menu → Automations dialog (template builder: move→assign, move→priority, created→label, due→comment); rule mutations need the ADMIN role; MCP tools `list_automations`/`create_automation`/`set_automation_enabled` (admin scope; surface now 53 tools counting the P2.6 webhook tools).

**Bulk edit + import/export (P3.8).** Board multi-select: shift-click toggles card selection (plain click opens the panel and clears); the floating `BulkActionBar` applies move/priority through the P2.3 bulk ops (`bulkMoveTasks`/`bulkUpdateTasks`, now also server actions) and label/assign/archive by fanning out the existing single ops (each keeps authz/Activity/events; not one transaction — see §9). `/[ws]/import` (linked from settings): CSV imports parse client-side via the stdlib parser in `src/lib/csv.ts` (RFC-4180; `toCsv` powers exports) with column mapping + dry-run preview; ops in `src/server/imports/operations.ts` (ADMIN role) — contacts are idempotent by externalId then lower(email) (matches update, never duplicate), tasks chunk through `bulkCreateTasks` 50 at a time (the op's transaction timeout is 30s — 1k rows verified live) with an optional skip-existing-titles knob; Trello board JSON imports lists→columns, cards→tasks (`mapTrelloExport`). Export: `GET /api/export?workspaceId=…[&boardId=…]&format=csv|json`, session-authed, archived excluded.

**Polish batch (P3.9).** Per-kind quick-create: `inline-task-create.tsx` shows kind-specific fields (CRM amount+contact, SUPPORT severity+contact, BUGS severity+version, ROADMAP quarter) applied to the auto-created sidecar via the existing update ops right after the create. Fine-grained realtime: the four sidecar `*.updated` events now carry a `patch` of the changed fields (built from the op's activity payload via `eventPatch`); `useBoardRealtime(boardId, onEvent)` lets the board apply `applySidecarPatch` (`src/components/board/realtime-patch.ts`, pure + unit-tested — ISO strings revive to Dates) in place, falling back to `router.refresh()` for everything else, and pusher-internal frames no longer trigger refreshes. Contact merge: `mergeContacts` op (one transaction: duplicate's deal links move with `skipDuplicates`, tickets repoint, empty survivor fields fill, duplicate deleted) behind the Merge button on `/[ws]/contacts` — UI-only surface, no Activity (contacts are not task-scoped).

**Agent identity (P4.1).** `ApiToken.displayName` + `ApiToken.emoji` are the token's teammate-facing identity (optional, set in the tokens UI at creation; OAuth access tokens auto-set `displayName` to the CIMD client name). `withSource` snapshots them into MCP-sourced activity payloads as `tokenDisplayName`/`tokenEmoji` next to the P2.8 `tokenId`/`tokenName` — a write-time snapshot, so badges survive token deletion/rename. Payload parsing lives in `src/lib/activity-source.ts` (`agentIdentityOf`, `matchesSourceFilter` — plain module shared by server pages and client components, same rule as `activity-verbs.ts`); the shared `AgentBadge` (`src/components/board/agent-badge.tsx`) renders `via <emoji> <displayName>` falling back to `🤖 <token name>` in the task activity feed, comment thread, and workspace-home digest. The task activity feed filters by source — All / Humans (`ui` + pre-P0.4 rows without `source`) / Agents (`mcp`) / System (`automation` + `system`) — and automation-sourced rows carry a "via ⚡ automation" chip (they run as the rule creator and would otherwise look human). Dev-only `/api/dev/mcp-token` accepts `displayName`/`emoji` for e2e.

**Reference agents (P4.2).** `agents/` is a standalone pnpm package (own lockfile via `.npmrc ignore-workspace`; excluded from the app's tsconfig/eslint, so its deps never enter the app tree) holding three reference agents that operate Stacks purely through the MCP surface on either of two runtimes selected by `STACKS_AGENT_PROVIDER`: the Claude Agent SDK (default; `allowedTools: ["mcp__stacks__*"]` — no filesystem/bash) or the OpenAI Codex SDK (`codex` — runs on a ChatGPT-subscription `codex login`, MCP server injected per-run via config overrides, shell tool disabled + read-only sandbox for the same tools-only world): `bug-triage.ts` (HMAC-verified `task.created` webhook receiver → severity + duplicate links + repro request, idempotency keys derived from delivery ids), `crm-follow-up.ts` (cron sweep → DRAFT follow-up comments on stale deals), `standup.ts` (read-scope-only daily digest splitting humans vs agents via `list_activity` source). Setup + cron lines in `agents/README.md`; sanity check is `cd agents && pnpm install && pnpm typecheck`.

**Semantic layer (P4.3).** pgvector on Neon: `Task.embedding` / `Contact.embedding` (`vector(1024)`, declared `Unsupported` in the Prisma schema, DDL in the hand-authored migration; read/written ONLY via raw SQL). Embeddings are provider-optional like Pusher/R2/Resend — Voyage AI over raw fetch (`src/lib/embeddings.ts`, gated on `VOYAGE_API_KEY`; model default `voyage-3.5-lite`, 1024 dims): absent key = the layer silently no-ops. The P3.6 cron sweep refreshes them: SQL computes both the embed text and its md5 (`embeddingHash`), so new AND edited rows are found by one predicate — no triggers, no write-path hooks, ~5-min freshness. Query layer `src/server/queries/similar.ts` (exact cosine KNN, archived excluded, no ANN index at current scale): `findSimilarToTask` (stored embedding, no provider call) / `findSimilarToQuery` (embeds the query, `input_type: "query"`) / `findDuplicateSuggestions` (similarity ≥ 0.8, already-linked pairs excluded). Surfaces: MCP tool `find_similar_tasks` (read class; taskId XOR workspaceId+query; surface now 54 tools — the count frozen by `tool-surface.test.ts`; provider-off returns empty + notice, never an error) and a "Possible duplicates" section on BUGS task panels proposing one-click `DUPLICATES` links via the existing `addTaskLink`.

### Auth
Auth.js v5 with `PrismaAdapter` and `session: { strategy: "database" }`. `src/auth.config.ts` is the Edge-safe subset (no DB) imported by middleware/proxy; `src/auth.ts` is the full Node config with the Resend provider and `events.createUser` → `markInstanceAdminIfFirst` + `ensurePersonalWorkspace`. Use `requireUser()` from `src/lib/session.ts` in server actions and protected pages — it redirects to `/login` when unauthenticated.

**Open sign-up + first-user admin (open-source build).** The `signIn` callback in `auth.ts` runs `isSignInAllowed(email)` (`src/server/auth/signup-gate.ts`) — the single gate, evaluated before the adapter's `createUser` for every provider/flow. This branch defaults to OPEN registration (`OPEN_SIGNUP` unset or truthy): any email may create an account. Set `OPEN_SIGNUP=false` (also `0`/`no`/`off`) for invite-only, where a NEW account is created only for the first-ever user (empty-DB bootstrap, `db.user.count() === 0`), an email matching `SIGNUP_ALLOWLIST` (comma/space-separated emails and/or `@domain` suffixes), or one with a pending unexpired workspace `Invitation`; otherwise `AccessDenied` (the email server action pre-checks the same helper so no magic link is sent, and `pages.error = "/login"` surfaces it as `?error=AccessDenied`). Existing users always sign in. Separately, `events.createUser` calls `markInstanceAdminIfFirst` (`src/server/auth/first-user.ts`): the first user on a fresh DB (`count === 1` post-insert) gets `User.isAdmin = true`, surfaced on `session.user.isAdmin` (no admin UI yet — it's a foundation). Don't add user-creating auth paths that bypass this gate.

### Data model
Prisma schema in `prisma/schema.prisma`. Key shapes: `Workspace` → `Board` → `Column` → `Task` with `Label`, `TaskAssignee`, `Subtask`, `Comment`, `Attachment`, `Activity` children. **Ordering is fractional `Float` positions** managed by `src/lib/position.ts` (`POSITION_STEP = 1024`, midpoint inserts, `rebalance` if gaps collapse). Don't use integer indices for ordering. Soft-delete is `archivedAt`; queries must filter `archivedAt: null`.

**Task identity.** `Task.workspaceId` is denormalized (write-once — tasks never move across boards) and `Task.number` is a per-workspace sequence allocated from `WorkspaceCounter` via an atomic upsert inside the `createTask` transaction — never assign numbers any other way. The human-readable key is `${Workspace.taskPrefix}-${Task.number}` (e.g. `STK-123`; prefix derived from the slug by `taskPrefixFromSlug` in `src/lib/slug.ts`). Every MCP response that returns tasks includes `number` + `key`, and `get_task` resolves `{ workspaceId, number }` as an alternative to `taskId`.

**Board kinds.** `Board.kind` is a `BoardKind` enum: `TASKS` (default), `CRM`, `SUPPORT`, `BUGS`, `ROADMAP` — all implemented. The kind controls which default columns `createBoard` seeds (`DEFAULT_COLUMNS` in `src/server/boards/operations.ts`) and which sidecar UI sections render in `task-detail-panel.tsx` / `task-card.tsx`. Boards can be converted between kinds (`convertBoardKind` in `src/server/boards/operations.ts`, ADMIN-only, MCP tool `convert_board_kind`): conversion eagerly backfills the target sidecar on every non-archived task in one transaction, reseeds nothing, preserves other-kind sidecars, and fires `board.kind_changed`. Each non-TASKS kind has a 1:1 sidecar on `Task` that `createTask` auto-creates when the column belongs to a board of that kind:

- **`CRM`** — `Contact` (workspace-scoped, managed at `/[workspaceSlug]/contacts`; ops in `src/server/contacts/`) + `Deal` (sidecar). Ops `updateDeal` / `setDealContacts` in `src/server/tasks/operations.ts`. `Contact.externalId` absorbed from the Customer merge. Event `deal.updated`. Activities `DEAL_UPDATED` / `CONTACT_LINKED` / `CONTACT_UNLINKED`. `Deal.amount` is `Decimal(15,2)` — convert to `Number` at every query boundary (see `src/server/queries/boards.ts`, `src/server/actions/columns.ts`, `src/server/queries/mcp-context.ts`).
- **`BUGS`** — `BugReport` (sidecar). Op `updateBugReport`. Event `bug.updated`. Activities `BUG_UPDATED` / `BUG_RESOLVED` / `BUG_REOPENED` (resolvedAt transition picks the verb).
- **`SUPPORT`** — `Ticket` (sidecar) linked to the shared `Contact` directory (`Ticket.contactId`, one contact per ticket). Ops `updateTicket` / `linkTicketContact`. Event `ticket.updated`. Activities `TICKET_UPDATED` / `CONTACT_LINKED` / `CONTACT_UNLINKED`. `Customer` was merged into `Contact` (P1.3 party merge): rows were merged by `(workspaceId, lower(email))`, `/[ws]/customers` redirects to `/[ws]/contacts` (page header "People"), and the `Customer` table + `Ticket.customerId` were dropped in the contract migration. `CUSTOMER_LINKED`/`CUSTOMER_UNLINKED` stay in the enum for historical activities only — never write them.
- **`ROADMAP`** — `Initiative` (sidecar: quarter, confidence, effort, RICE). Op `updateInitiative` (+ read `listInitiatives`). Event `initiative.updated`. Activity `INITIATIVE_UPDATED`. Dependencies between initiatives go through the universal task-link graph (below) — there are no initiative-specific edges anymore.

**Task links.** `TaskLink` connects tasks of **any** board kind within one workspace (directional `from → to`, composite PK `[fromTaskId, toTaskId, kind]`, `TaskLinkKind` = `BLOCKS | DEPENDS_ON | RELATES_TO | DUPLICATES`). Ops `addTaskLink` / `removeTaskLink` / `listTaskLinks` in `operations.ts`; adding an existing edge is a no-op, removing a missing edge is a no-op. Cycle prevention for BLOCKS/DEPENDS_ON via `findCyclePath` in `src/server/links/graph.ts` — the rejection error names the cycle path by task key (e.g. `STK-7 → STK-6 → STK-7`). `DEPENDENCY_ADDED` / `DEPENDENCY_REMOVED` activities are written on **both** endpoint tasks with `kind` in the payload, and `task.updated` fires to both endpoint boards. Cards show a red "Blocked" badge when a non-archived task BLOCKS them. `InitiativeDependency` was migrated into `TaskLink` and dropped in the contract migration.

When adding new `ActivityType` values, remember Postgres enums are append-only — only add at the end of the enum block in `prisma/schema.prisma`.

### Prisma client gotchas
- `src/lib/db.ts` uses a lazy `Proxy` singleton (constructs on first access) so importing `db` doesn't throw when `DATABASE_URL` is unset at module load (matters during Next prerender).
- **Do not import enum values from `@prisma/client` in Client Components** — it pulls the browser shim and bloats the bundle. Use the mirror constants in `src/lib/enums.ts` instead. Server code can import either.

### Realtime
`src/lib/pusher-server.ts` exports `triggerBoardEvent(boardId, event, payload)` (channel `private-board-${boardId}`). Client subscription is `src/hooks/use-board-realtime.ts`, which currently just calls `router.refresh()` on any event. When adding a new mutation that should sync across users, fire a Pusher event with one of the typed `BoardEvent` strings.

### Imports & conventions
- `@/*` → `src/*` (see `tsconfig.json`).
- shadcn config is in `components.json` (style `base-nova`, base color `neutral`, icons `lucide`). UI primitives live in `src/components/ui/`.
- **Base UI menu, not Radix**: `DropdownMenuItem` here wraps `@base-ui/react`. Use `onClick`, not `onSelect` (the latter silently no-ops).
- Prettier: 2-space, double quotes, trailing commas, 80 cols, with tailwindcss class sorting.
